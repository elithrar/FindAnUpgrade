## Findings at the reviewed commit

1. **P1 — Pending first-window items starve all later metadata.** `SearchModel.lua:117` appends only the first 128 pending IDs to `needed`; `Search.lua:128` deduplicates dispatch against session `itemRequests` without excluding those dispatched IDs from future windows. With the production workload and no callbacks for the first window, 1,000 ticks plus a deliberate refresh still dispatch only 128 of 1,344 eligible IDs. Explicit false load-result callbacks also retain this same window and never reach the remaining IDs. A single finite page must not be blocked by earlier failed or stalled requests. Keep deduplicated attempts, advance queue coverage independently of successes, and verify both item and quest queues under failures and repeated refreshes.

2. **P2 — Matching callback floods can defer refresh indefinitely.** `Search.lua:93` resets `changeAt` to the latest event time plus 0.15 seconds. One matching `QUEST_DATA_LOAD_RESULT` every 0.1 seconds for ten seconds produces zero refreshes and leaves `dirty=true`. Coalesce arrivals with a maximum deadline so active data work makes visible progress during sustained arrivals, while preserving open owned inspection/menu interactions.

3. **P2 — Successful hidden item arrivals leave a stale pending cache after reopening.** The event handler's early visibility return at `Search.lua:84` precedes invalidation. `SearchModel.lua:68` immediately returns any cached item, including pending rows, and reopening resets request ownership without revalidating pending metadata. The probe requests item 60, hides search, changes native cache readiness to true, delivers its successful result event, and reopens: the item remains pending although the native cache predicate is true. Invalidate relevant pending cache entries while hidden or recheck their readiness on the next query. Do not depend on a new event for an already loaded item.

4. **P2 — Request dispatch depends on frame rate.** `Search.lua:128` runs two dispatch iterations on every delivered frame and has no elapsed-time gate. Missing quest levels produce 30/60/144/240 native quest load requests in one second at 30/60/144/240 FPS; cold items produce 60/120 requests per second at 30/60 FPS, exhausting the current 128-item window still faster at higher FPS. These are observed mock call counts, not a proven native server limit violation. Use a finite time budget and bound catch-up after long frames; validate equivalent request counts at differing frame rates and during synchronous result callbacks.

5. **P3 — A settled visible search retains permanent idle frame work.** `Search.lua:118` installs its updater until hide, regardless of whether indexing, requests, deadlines, dirty state or inspection are active. In a settled warm search, 1,000 delivered idle frames call `Menu.GetManager` 1,000 times. No metadata/query work occurs in those frames, but the callback remains installed. Stop it when owned work ends and wake it from the actual change, arrival, menu/inspection or pointer entry that requires work. Hidden search correctly removes the updater and produces zero such calls.

Warm full-catalog query performance is an additional optimization observation, not a standalone correctness blocker. Over 100 warmed blank/all-level queries, the observed median was 6.21 ms and maximum 12.45 ms. Each query rereads title and difficulty for all 1,267 quests (2,534 native-facing reads) before eligibility checks and sorting. This can become a visible hitch under event churn; cache ready metadata with an explicit invalidation policy and measure the actual client before claiming a native frame budget.

## API, ownership and restrictions

The local current source snapshot reports Forever `1.60.1.70374`, interface `16001`, revision `735496de78ebd30ce816a0637982c556987f258c`; its quest/tooltip contracts and comparison implementation match the pinned hashes. The separate baseline detail renderer remains `943764493e6b16d63ded3ab304150d1f05e58b57` (70338).

Exact-ID title, difficulty, completion, repeatability, disabled and quest-log queries use the declared shapes; quest load results carry quest ID and success. These contracts do not establish that loading an arbitrary unaccepted quest hydrates difficulty. The finder correctly excludes unreadable/invalid difficulty rather than inferring it from recorded minimum level. Source: [matching quest contract](https://github.com/Gethe/wow-ui-source/blob/735496de78ebd30ce816a0637982c556987f258c/Interface/AddOns/Blizzard_APIDocumentationGenerated/QuestLogDocumentation.lua).

Full item reads use return positions 1-5, 9-10 correctly and are gated on readable cache readiness; instant reads use positions 4-5. Both metadata APIs may return no data. Matching item events carry ID and success and may be synchronous. The reviewed handler does not consume success; queue progress and negative-cache lifetime therefore need explicit handling. Source: [matching item contract](https://github.com/Gethe/wow-ui-source/blob/735496de78ebd30ce816a0637982c556987f258c/Interface/AddOns/Blizzard_APIDocumentationGenerated/ItemDocumentation.lua).

Equipment locations use the colon receiver required by [ItemLocation](https://github.com/Gethe/wow-ui-source/blob/735496de78ebd30ce816a0637982c556987f258c/Interface/AddOns/Blizzard_ObjectAPI/Mainline/ItemLocation.lua); waypoint points use the static dot call required by [UiMapPoint](https://github.com/Gethe/wow-ui-source/blob/735496de78ebd30ce816a0637982c556987f258c/Interface/AddOns/Blizzard_ObjectAPI/Mainline/UiMapPoint.lua). Waypoint dispatch is explicit menu input and accepts only strict successful native set before supertracking.

Owned reward tooltips validate exact item type/ID and reject inaccessible nested tooltip data before invoking an owned copy of current native comparison methods. Reward choice metadata distinguishes mixed exposed indices from item-only tooltip indices and suppresses ambiguous unresolved slots. The native explicit quest-ID overload semantics for mixed choices remain a live/source-contract limitation already documented in the prior API review. No quest selection/accept/completion, native frame layout/visibility write, shared native comparison state write, or other addon's data write was found in these reviewed paths.

The launcher creates one owned button, owns its drag updater, ends drag work on hide/release, and suppresses the release click. Search cards/icons are pooled by viewport high-water mark; scrolling reuses them. Full-result layout/visible range scans are linear in query output, with only viewport cards filled. The Core hover updater removes itself after its source and popup lifetimes end. Persistent search updater behavior is the exception identified above.

Secret/readability and combat guards are source checks, not a taint verdict. `pcall` cannot establish permission for a restricted native operation. The inspected contract annotations accept ordinary catalog IDs, and unreadable player/item/tooltip values are rejected before arithmetic/string conversion. Live secret behavior and protected-frame interactions still require the relevant client.
